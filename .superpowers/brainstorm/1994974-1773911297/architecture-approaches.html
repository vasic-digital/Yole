System Architecture: 3 Approaches

How should the Autonomous QA Session orchestrate all components?

A

Centralized Pipeline

A single SessionOrchestrator in HelixQA drives everything sequentially:

// Sequential phases, one controller
1. LLMsVerifier → Score & select LLMs
2. DocProcessor → Build feature map
3. VisionEngine → Init screen capture
4. LLMOrchestrator → Spawn CLI agents
5. Navigation Loop:
  → Vision captures screen
  → LLM analyzes + decides action
  → Execute action on app
  → Check feature map coverage
  → Generate tickets for issues
6. Report → Final QA report + tickets

Pros

  • Simple mental model
  • Easy to debug (linear flow)
  • Predictable resource usage

Cons

  • One agent at a time (slow)
  • Single point of failure
  • Hard to parallelize platforms
B

Event-Driven Pipeline

Modules communicate via Go channels. Each module is a goroutine consuming/producing events:

// Concurrent producers & consumers
DocProcessor →ch→ FeatureMap
VisionEngine →ch→ ScreenState
Navigator ←ch← ScreenState + FeatureMap
Navigator →ch→ Actions
IssueDetector ←ch← ScreenState
IssueDetector →ch→ Tickets
EvidenceRecorder ←ch← All events

Pros

  • Naturally concurrent
  • Modules are decoupled
  • Easy to add new consumers

Cons

  • Complex event ordering
  • Harder to debug (async)
  • Channel deadlock risks
C

Coordinator + Worker Agents

A SessionCoordinator manages phases, but delegates work to parallel worker agents per platform:

// Phased coordination, parallel execution
SessionCoordinator
├─ Phase 1: Setup (sequential)
│  ├─ LLMsVerifier → select LLMs
│  ├─ DocProcessor → build feature map
│  └─ LLMOrchestrator → spawn agents
├─ Phase 2: Doc-Driven (parallel per platform)
│  ├─ Worker[Android] → verify features
│  ├─ Worker[Desktop] → verify features
│  └─ Worker[Web] → verify features
├─ Phase 3: Curiosity (parallel per platform)
│  ├─ Worker[Android] → free explore
│  ├─ Worker[Desktop] → free explore
│  └─ Worker[Web] → free explore
└─ Phase 4: Report (sequential)
   └─ Aggregate tickets + evidence + report

Pros

  • Clear phase boundaries
  • Parallel platform testing
  • Predictable + concurrent
  • Easy progress tracking

Cons

  • Slightly more complex than A
  • Cross-platform issues found late
