Design Section 5: DocProcessor Module

Load project documentation, build feature maps, track verification coverage

Core Interfaces
// ═══ Document Loader ═══
type Loader interface {
  LoadDir(ctx, path string) ([]Document, error)
  LoadFile(ctx, path string) (Document, error)
  SupportedFormats() []string
}
// ═══ Feature Map Builder ═══
type FeatureMapBuilder interface {
  BuildFromDocs(ctx, []Document) (*FeatureMap, error)
  Enrich(ctx, fm *FeatureMap, agent LLMAgent) error // LLM refines map
  Merge(maps ...*FeatureMap) *FeatureMap
}
// ═══ Coverage Tracker ═══
type CoverageTracker interface {
  MarkVerified(featureID string, platform string, evidence Evidence)
  MarkFailed(featureID string, platform string, issue Issue)
  MarkSkipped(featureID string, platform string, reason string)
  Coverage() CoverageReport
  CoverageByPlatform(platform string) float64
  CoverageByCategory(category string) float64
  Unverified() []Feature
  Export() CoverageSnapshot
}
// ═══ LLM Agent (injected from LLMOrchestrator) ═══
type LLMAgent interface {
  Summarize(ctx, text string) (string, error)
  ExtractFeatures(ctx, text string) ([]RawFeature, error)
  ClassifyFeature(ctx, feature RawFeature) (FeatureCategory, error)
  InferScreens(ctx, features []Feature) ([]ExpectedScreen, error)
  GenerateTestSteps(ctx, feature Feature) ([]TestStep, error)
}
Document Processing Pipeline
═══ Phase 1: Load & Parse ═══
Scan project tree for all documentation files
Supported Formats
*.md (Markdown) ← primary
*.yaml / *.yml (configs)
*.txt (plain text)
*.html (web docs)
*.adoc (AsciiDoc)
*.rst (reStructuredText)
Auto-Discovered Locations
docs/ directory
README.md, CLAUDE.md
**/USER_GUIDE.md
**/API_REFERENCE.md
**/ARCHITECTURE.md
CHANGELOG.md, CONTRIBUTING.md
═══ Phase 2: Extract Features (LLM-Powered) ═══
LLM reads each document, extracts features, screens, workflows
Document: "docs/USER_GUIDE_FORMATS.md"
────────────────────────────────
LLM extracts:
→ Feature: "Markdown editing" (category: format, screens: [editor, preview])
→ Feature: "CSV import/export" (category: format, screens: [file_picker, editor, export_dialog])
→ Feature: "Dark theme toggle" (category: ui, screens: [settings])
→ Feature: "Cloud storage sync" (category: network, screens: [storage_config, sync_status])
→ Workflow: "Create new markdown doc" (steps: [open_app → new_doc → select_format → type → save])
═══ Phase 3: Build Feature Map ═══
Structured, queryable map of everything the app should do
FeatureMap
├─ Features[] // flat list, each with ID, name, category, platforms, source doc
├─ Screens[] // expected screens with descriptions, linked features
├─ Workflows[] // multi-step user journeys with expected outcomes
├─ Categories{} // grouped: format, ui, network, settings, etc.
├─ PlatformMatrix{} // which features on which platforms
└─ DocGraph // link relationships between documents
═══ Phase 4: Generate Verification Plan ═══
LLM generates test steps for each feature, prioritized by risk
Feature "Markdown editing" → TestSteps:
  1. Open app → verify editor screen loads
  2. Create new markdown file
  3. Type "# Hello" → verify heading renders in preview
  4. Add bold, italic, link → verify formatting
  5. Save file → verify file persists after restart

Priority: critical (core feature, all platforms)
Key Data Types
type Document struct {
  Path      string       // relative to project root
  Format    string       // markdown, yaml, html, etc.
  Title     string       // extracted or inferred title
  Content   string       // raw content
  Sections  []Section    // parsed heading structure
  Links     []string     // outgoing doc references
  ModifiedAt time.Time
}
type Feature struct {
  ID         string      // auto-generated: "feat-markdown-editing"
  Name       string
  Description string
  Category   FeatureCategory // format, ui, network, settings, etc.
  Platforms  []string    // [android, desktop, web]
  Priority   string      // critical, high, medium, low
  Screens    []string    // expected screen IDs
  TestSteps  []TestStep  // LLM-generated verification steps
  SourceDoc  string      // which doc defined this feature
  SourceSection string   // heading path within doc
}
type FeatureMap struct {
  Features      []Feature
  Screens       []ExpectedScreen
  Workflows     []Workflow
  Categories    map[FeatureCategory][]Feature
  PlatformMatrix map[string][]Feature // platform → features
  DocGraph      *DocGraph
  GeneratedAt   time.Time
  ProjectRoot   string
}
type CoverageReport struct {
  Total         int
  Verified      int
  Failed        int
  Skipped       int
  Unverified    int
  OverallPct    float64
  ByPlatform    map[string]float64
  ByCategory    map[string]float64
  Issues        []Issue
}

Key Design Decisions

  • LLMAgent is injected — DocProcessor doesn't depend on LLMOrchestrator at module level. The caller passes an adapter that satisfies the LLMAgent interface. This keeps DocProcessor reusable by any project.
  • Auto-discovery — Scanner finds docs by well-known patterns (docs/, README.md, *_GUIDE.md, etc.) plus configurable additional paths. No manual enumeration needed.
  • CoverageTracker is thread-safe — multiple platform workers mark features as verified/failed concurrently during parallel testing.
  • Feature IDs are deterministic — generated from name + category, so the same feature always gets the same ID across runs. Enables progress comparison between sessions.
  • Prompt templates in prompts.go — structured prompts with JSON output schema for feature extraction. Versioned so changes are trackable.
